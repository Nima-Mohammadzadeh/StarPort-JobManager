# SGTIN-198 encoding for standard jobs — design

Date: 2026-11-10 · Status: implemented

## Purpose

Some customers need tags encoded as **SGTIN-198** (GTIN + alphanumeric serial of up to 20 characters)
instead of the **SGTIN-96** the app writes today. An operator creating a standard job can choose the
encoding. Everything downstream (serial safety, rolls, data files, tag check, rewind page, add data)
keeps working for either encoding.

## Decisions (agreed)

- **Approach:** the encoding is a property of the job (`epc_scheme`). It is not a new data-sheet type like GO2/CDO.
- **Serials stay numeric in the registry.** The serial registry keeps counting integers and never reuses one.
  A *serial format* decides how that integer is written into the EPC. Only `number` exists now:
  serial `123` is written as the characters `"123"`. Prefix + counter and customer-supplied serials are later work.
- **Choice lives behind "Advanced"** on the New job form. SGTIN-96 stays the default.
- **Standard jobs only.** Special, GO2 and CDO jobs hide the option (they have no UPC / are raw-hex sheets).
- **One more scheme later:** none is chosen. The design only guarantees that adding one is a new encoder
  function plus one table entry.
- The scheme is fixed when the job is made and never changes, including for added data.

## Out of scope

SGTIN-198 serial formats other than `number`; any scheme other than SGTIN-96/198; changing a job's
scheme after creation; converting existing jobs.

## Data model

Two columns added to `jobs` with the existing `add_col` pattern in `init_db()`:

| Column | Type | Default | Meaning |
|---|---|---|---|
| `epc_scheme` | TEXT NOT NULL | `'sgtin96'` | `sgtin96` or `sgtin198` |
| `serial_format` | TEXT NOT NULL | `'number'` | how the integer serial becomes the EPC serial |

Existing jobs get the defaults, so nothing is migrated. `job_rolls.epc_start/epc_end` already hold text and
hold the longer value as is. `job_additions` rows follow the job's scheme.

## Encoder (`generators.py`)

- `generate_epc(upc, serial, scheme="sgtin96", serial_format="number")` dispatches through a table
  `EPC_SCHEMES = {"sgtin96": ..., "sgtin198": ...}` of `{encode, decode, header, hex_len, label}`.
  The SGTIN-96 code is moved unchanged into `_encode_sgtin96`.
- `_encode_sgtin198`: header `0x36` (8 bits), filter `001` (3), partition `101` (3, same UPC split as today),
  company prefix 24 bits and item reference 20 bits (44 total), serial 140 bits = 20 characters x 7-bit ASCII,
  zero-padded on the right. 198 bits are written as **50 hex characters** with 2 zero padding bits at the end.
- `decode_epc(hex)` picks the scheme from the header byte (`30` or `36`) and returns
  `{"scheme", "upc", "serial"}`. For SGTIN-198 the serial is returned as an integer when it is all digits,
  otherwise decoding reports "not one of our EPCs" for the registry lookup (the string is still returned).
- Refused with a clear message: a serial longer than 20 characters; a character outside 7-bit ASCII; an EPC
  whose length or header does not match its scheme.
- The exact bit layout, serial character set and padding rule are checked against the GS1 EPC Tag Data
  Standard text before coding, and a worked example from that standard is a test.
- `roll_plan`, `generate_db_files` and `_write_xlsx` take the scheme and call the dispatcher. The files keep
  the columns `Serial #`, `UPC`, `EPC`. After writing, each file is re-read and every EPC is decoded and
  compared with its row (UPC, serial, scheme), as the GO2 and CDO files already are.

## Everything that assumed 24 hex characters

| Place | Change |
|---|---|
| `app.py` `_lookup` / `_clean_epc` | accept 24 or 50 hex characters; the run-extraction regex and the "an EPC is 24" message become scheme aware; the "starts with 30" check becomes "starts with a known header"; the TID (`E2`) check is unchanged |
| `index.html` `verifyEpc` / `epcParts` | length check `24` or `50`; compare scheme + UPC prefix, then the serial range, using the shared decode rules |
| `index.html` roll card tag range table | the full EPC is shown without the hex-tail highlight for SGTIN-198; a separate **Serial tail** shows the last 5 characters of the serial |
| `rewind.html` | `r.epc.length === 24` becomes length-by-scheme; the 5-character "tail" for SGTIN-198 is the last 5 characters of the serial, because the last hex characters of a right-padded EPC are mostly zeros |
| Roll API payload | rolls and lookups carry `epc_scheme` so the pages never guess from length |
| Job details dialog | shows the scheme, e.g. "EPC encoding: SGTIN-198" |
| `generators.qc_html` / `checklist_generator.py` | show whatever EPC the roll holds; `checklist_generator.py` has no EPC references; `qc_html` prints the last 5 hex characters of each roll's first and last EPC, so for SGTIN-198 it prints the serial tail instead (`tag_tail`) |

## New job form

- A collapsed **Advanced** area with **EPC encoding**: SGTIN-96 (default) or SGTIN-198. Choosing SGTIN-198
  shows **Serial format: Number** (only choice).
- The preview shows the scheme name and the first and last EPC before any serial is taken.
- Hidden for Special, GO2 and CDO jobs.
- Server side: the scheme is validated against the allowed list and against the job type; an unknown scheme or
  a scheme sent for a special/sheet job is refused.

## Add data to a job

Uses the job's `epc_scheme` and `serial_format`. Preview, new rolls, `_ADD<n>` files and the post-write check
all produce and verify EPCs in that scheme. The UI does not offer a different scheme.

## Testing

- **Encoder:** round trip encode/decode for many UPCs and serials; header byte `0x36`; 50-hex length and
  padding bits; a worked example from the GS1 TDS; 1, 10 and 20 character serials; 21 characters and non-ASCII
  refused.
- **No regression:** SGTIN-96 output for existing inputs is byte-for-byte the same, and a job with default
  columns behaves as before.
- **Job flow:** create an SGTIN-198 job (files, rolls, QC sheet), tag check accepts a right tag and rejects a wrong
  product / wrong scheme / wrong length, add data extends it in the same scheme, rewind lookup finds the roll.
- **Server rules:** scheme refused for special/GO2/CDO jobs and for unknown values.
- **UI:** run through the encoding-floor-sandbox with a demo SGTIN-198 job: roll card, tag check, job dialog,
  rewind page at desktop and tablet widths.

## Risks

- The padding and character rules must match the standard exactly, or readers will decode different serials.
  Mitigated by the standard's worked example as a test.
- Tag memory length (the EPC length in the tag's protocol-control word) is set by the encoding software or
  printer, not by this app. The app only produces the EPC value; whether the customer's printer or reader
  accepts a 50-hex value is confirmed with a real sample before the first production job.
